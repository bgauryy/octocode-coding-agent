# Context engineering, sessions and prompt caching: octocode-code vs oh-my-pi

This review compares how octocode-code and [oh-my-pi](https://github.com/can1357/oh-my-pi) (omp) build the prompt, manage the context window, prune tool output, store sessions, use provider prompt caches, brief subagents and carry context across sessions. Both projects are Pi forks, so several mechanisms share an origin; the differences are in what each fork added.

**Bottom line.** omp invests in _more ways to shrink context_: native provider compaction, image-based history archives (snapcompact), in-place artifact elision (shake), cache-lookback-aware pruning, per-model tokenizers and configurable thresholds. octocode-code invests in _cheaper and recoverable compaction_: the summary is requested inside the session's own cached request, tool results are cleared only after the cache has gone cold, and everything removed stays reachable through saved files and a searchable archive. omp has mid-stream rules (TTSR), multi-process session leases and subagent cache-key families; octocode-code has default-on budgeted memory, per-entry flushed transcripts, a two-layer cache retention policy and post-compaction file restore.

## 1. System prompt assembly

**octocode-code.** `buildSystemPromptSections` emits ordered sections: `preamble`, `tools`, `rules`, `docs`, then `addendum`, `project_context`, `skills`, `cwd`, then custom sections such as Octocode's `octocode_work` or `role` (`core/system-prompt.ts:151-198`). Context files are the first of `AGENTS.override.md`, `AGENTS.md`, `CLAUDE.md` per directory from the repository root to cwd, capped at 64 KiB each (`core/resource-loader/context-files.ts:29`, `:41`, `:88-130`). The skill list fits an 8,000-character budget (`core/skills.ts:50`). Octocode rebuilds its sections only when their inputs change (`octocode/turn.ts:72-76`), and a changed section reaches the model as a patch rather than a rewritten prompt (`core/system-prompt.ts:224-236`, `core/agent-session/tool-loadout.ts:299-312`). The leading prompt is split into two instruction cache blocks after `docs`, so project and session sections do not invalidate the base block (`core/model-runtime/instruction-boundary.ts:7-19`; disable with `OCTOCODE_INSTRUCTION_CACHE_SPLIT=off`). No date is injected.

**omp.** Block 0 is the instruction template; all cwd-derived data sits in one trailing `<project-context>` block (`packages/coding-agent/src/system-prompt.ts#L1026-L1041`). The Anthropic adapter places its head breakpoint before the first `<memories>` or `<project-context>` block (`packages/ai/src/providers/anthropic.ts#L4883-L4910`). Date and cwd ride a reminder on the first user turn, so day rollover and directory changes do not touch the tool array (`packages/coding-agent/src/session/date-cwd-reminder.ts#L1-L12`). Context-file discovery is broader (`.omp/`, `.claude/`, `.gemini/`, Copilot files) with priority shadowing _(omp doc: `docs/context-files.md`)_. Subagents drop `AGENTS.md` but keep `CLAUDE.md` _(omp doc: `docs/system-prompt-customization.md#L87-L95`)_.

**Difference.** Both separate stable from project-specific text for caching. omp goes further by keeping cwd and date out of the system prompt entirely; ours keeps `cwd` in the second instruction block, which is cheap because cwd rarely changes within a session.

**Summarization.** Ours runs one LLM summary. The Octocode extension first appends a checkpoint request to the session's own request (same system, tools, messages and routing id), so the provider can read the prefix from cache (`octocode/compaction/shared-summary.ts:14-29`, `:83-156`); otherwise it calls the standalone summarizer, which sends no cache markers (`core/compaction/summarization.ts:122-125`). The Octocode summary adds errors and fixes, where work stopped, follow-ups, verbatim user messages (60,000 characters total), saved-result paths and a recovery block naming the archive (`octocode/compaction/summary.ts:75-117`, `octocode/compaction/checkpoint-text.ts:20-22`). After compaction, up to five recently edited files are restored into context (`octocode/compaction/restore.ts:27-31`). Branch summaries on `/tree` use the standalone path and never share the cache (`core/compaction/branch-summarization.ts:350`).

omp tries methods in order and advances on failure (`packages/coding-agent/src/session/compaction-methods.ts#L44-L51`):

1. `remote`: provider-native compaction. V2 streamed Responses keeps real user messages within 64,000 tokens (`packages/agent/src/compaction/compaction-v2-streaming.ts#L46`); then OpenAI `/responses/compact` and Anthropic's `compact-2026-09-04` beta (`packages/ai/src/providers/anthropic-wire.ts#L171-L172`).
2. `snapcompact`: no LLM call; discarded history is rendered to PNG frames for vision models, up to 80 frames (`packages/snapcompact/src/snapcompact.ts#L510`).
3. `handoff`: cache-aligned side request reusing the live prefix and key _(omp doc: `docs/handoff-generation-pipeline.md#L84-L85`)_.
4. `shake`: replaces large tool results and blocks with `artifact://` references, protecting the newest 16,000 tokens (`packages/agent/src/compaction/shake.ts#L49`).
5. `soft`: LLM summary with tool results cut to 2,000 characters (`packages/agent/src/compaction/utils.ts#L209-L217`).

## 3. Tool output and pruning

**Inline caps.** Both cap tool output at 50 KB (ours 2,000 lines, `core/tools/truncate.ts:11-12`; omp 3,000 lines, `packages/tui/src/tools/streaming-output.ts#L11-L13`) and spill the full text to a file. Ours writes spills into a per-session folder swept after 30 days (`octocode/shared/spill.ts:96-130`, `octocode/sessions/sweep.ts:25`) and adds a per-message budget of 60,000 characters per text part and 200,000 per assistant message (`octocode/shared/turn-budget.ts:7-9`). omp writes artifacts up to 16 MiB with head and tail (`streaming-output.ts#L17-L26`).

**Old results: the main philosophical difference.**

- Ours clears old results of re-fetchable tools only when the cache lifetime has already passed, because the next request rewrites the cache anyway. It keeps the newest 5 results, acts only when at least 20,000 tokens are freed, saves each result first and names the file in the placeholder. The decision is stored as a session entry and replayed on every request, so the prompt stays byte-stable across resume and fork (`octocode/compaction/clearing.ts:23-43`, `:130-185`).
- omp prunes while the cache may be warm but avoids the model's cache-lookback window (Claude: 20 positions): it protects the newest 40,000 tool-output tokens, requires 20,000 tokens of savings and skips results under 50 tokens (`packages/agent/src/compaction/pruning.ts#L77-L79`, `#L193`, `#L292`). It also replaces superseded reads of the same file and results that tools flag as useless (`pruning.ts#L118-L121`).

Ours never pays a cache rewrite to prune but cannot prune during a long warm session; omp prunes sooner and relies on placement to limit cache damage. Ours keeps every pruned byte recoverable on disk; omp's `[Output truncated - N tokens]` placeholder does not point to a copy (`pruning.ts#L280-L281`). For repeated reads, ours replaces the second read of an unchanged file with a short note (`octocode/files/dedupe.ts:86-127`), which is the mirror image of omp's supersede rule.

## 5. Prompt caching

**Retention.** Ours has two layers: instructions (tools plus leading system prompt) default to `long`, history to `short` (`core/settings-defaults.ts:58-59`); `cacheRetention: none` disables both (`packages/ai/src/utils/cache-policy.ts:18-42`). omp has one `cacheRetention` whose `auto` gives 1h entries on OAuth subscriber seats and 5m on API keys (`packages/ai/src/providers/anthropic.ts#L775-L788`).

**Anthropic markers.** Both stay within four breakpoints. Ours marks the system blocks, the last tool, the history tail and a lookback marker on the previous tail, because Anthropic looks back only 20 blocks (`packages/ai/src/api/anthropic-messages/cache-breakpoints.ts:41-85`). omp marks the stable head (last tool and last stable system block), up to two tail candidates, and a decimation checkpoint every 15 user turns (`anthropic.ts#L4701-L4702`, `#L4832-L4846`), which gives long sessions an older anchor to fall back to.

**OpenAI.** Both send `prompt_cache_key` derived from the session id, clamped to 64 characters (ours `packages/ai/src/api/openai-prompt-cache.ts:10-17`; omp `packages/ai/src/providers/openai-shared.ts#L554-L557`). Ours uses explicit `prompt_cache_options` (12h) on models that support it and 24h retention otherwise (`openai-prompt-cache.ts:47-69`). omp adds a subagent key family `<parent>:<agent>` (`packages/coding-agent/src/task/executor.ts#L4789-L4791`). Neither creates Gemini context caches; both only read `cachedContentTokenCount`.

**Warming.** Both warmers come from upstream Pi and share their constants: refresh at `min(0.9·TTL, TTL − 10 s)`, $0.05 minimum expected saving, 60/30-minute streaming/idle horizons, 0.15 idle continuation probability (ours `core/cache-warmer/economics.ts:17-33`; omp `packages/coding-agent/src/session/cache-warmer.ts#L59-L76`). Ours defaults to `streaming` and replaces the fixed idle probability with the session's own gap history in interactive mode (`octocode/compaction/cache.ts:141-166`). omp defaults to `idle`, turns warming off for subagents (`executor.ts#L4685-L4686`) and times idle compaction to fire before a 1h entry expires _(omp doc: `docs/compaction.md#L142-L144`)_.

**Reporting.** Ours shows hit rate, policy, warming and costs in `/status` and can flag large misses (off by default) (`core/cache-stats.ts:225-249`, `core/settings-defaults.ts:27`). omp shows cache read/write in the footer and a stats dashboard with cache savings (`packages/stats/README.md#L17-L18`).

## 6. Subagents

Ours runs each child as a separate Octocode process in RPC mode with its own tool allow-list and skills (`octocode/subagents/process/session.ts:41-59`), up to 6 at once (`octocode/subagents/claim.ts:19-26`). The child gets the parent's prompt sections with `docs` blanked, a `## You` identity block and, after parent compaction, an archive pointer instead of the transcript (`octocode/turn.ts:79-93`, `octocode/instructions/task.ts:20-37`). Isolated worktree children name the main checkout in their prompt so siblings share a prefix (`octocode/turn.ts:80-88`). Reports are previewed at 8 KiB / 200 lines with the full text saved (`octocode/subagents/report.ts:17`).

omp renders a per-spawn role block after the shared footer so spawns of one agent share the static prefix, and gives children the `<parent>:<agent>` cache key (`executor.ts#L3949-L3985`, `#L4789-L4791`). Subagents always run mid-turn compaction checks, and a soft request budget injects a wrap-up notice with a hard stop at 1.5× (`executor.ts#L1787-L1802`). Results come back as a `<task-result>` envelope with a 5,000-character preview and an `agent://` pointer (`packages/coding-agent/src/task/result-summary.ts#L17-L26`). Neither system has a token budget for the child's context.

## 7. Durable and cross-session context

- **Memory.** Ours injects relevant SQLite memories before each prompt as a hidden message with a staleness header, budgeted at 1,200 characters for pinned and 2,400 overall, and loads project memories only in trusted projects (`octocode/memory/inject.ts:8-13`, `octocode/memory/register.ts:46-84`). omp's memory is off by default; backends are `local`, `hindsight`, `mnemopi` and `sharpshooter`, plus a `learned.md` lesson list _(omp doc: `docs/memory.md`)_; `memories.enabled` defaults to `false` (`packages/coding-agent/src/memories/settings.ts#L11-L14`).
- **Rules.** omp's TTSR matches regex, AST or judged conditions against the stream as it is generated, aborts, discards the partial output and retries with a `<system-interrupt>`; defaults `repeatMode: once`, `repeatGap: 10` (`packages/coding-agent/src/export/ttsr-settings.ts`; _omp doc: `docs/ttsr-injection-lifecycle.md`_). Ours has no conditional or stream-triggered rules (searched `packages/coding-agent/src`).
- **History.** Ours archives each compacted segment as Markdown with a `LIBRARY.md` index and exposes it, forked-from sessions, the parent session and same-repository sessions through the `archive` tool (`octocode/compaction/archive.ts:85`, `octocode/shared/history.ts:13-16`). omp exposes `history://` transcripts _(omp doc: `docs/compaction.md#L176-L183`)_.

## Verdict

Neither is better overall; they optimize for different things.

- **omp is ahead on breadth and long sessions:** more compaction methods, configurable thresholds, exact tokenizers, an older cache anchor for long Anthropic sessions, mid-stream rules, cross-process session leases and subagent budgets.
- **octocode-code is ahead on cost safety, recoverability and durability:** pruning never forces a cache rewrite, every removed byte stays reachable (spill files, the compaction archive, the `archive` tool), transcripts are flushed per entry, cache retention is set per layer, and memory works by default.
- **The cores are close:** both lay the prompt out for caching, both make the summary request cheap by reusing the cached prefix, and both cache warmers share upstream Pi's economics.

In practice: omp's extra machinery pays off in very long, single-model sessions with many concurrent processes. For typical sessions, ours spends less and loses nothing. That judgement is an inference from the code; neither system was measured live.
