# Plugins, skills, packages and hooks

How Octocode's four customization systems relate, how it adapts Claude Code and Codex formats, and how that compatibility is checked. To use them, start with [the guide](../PLUGINS.md). The current contracts live with their owners:

| System  | What it is                                                                                            | Contract                                                                                                                  |
| ------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Plugin  | A distribution container with identity and component declarations; a marketplace installs and updates | [Plugins](../packages/coding-agent/docs/plugins.md)                                                                       |
| Skill   | Task instructions, normally a folder with `SKILL.md`; the model reads the body when needed            | [Skills](../packages/coding-agent/docs/skills.md)                                                                         |
| Package | Octocode's own npm or git distribution of skills, prompts and themes; not a plugin manifest           | [Packages](../packages/coding-agent/docs/packages.md)                                                                     |
| Hook    | A handler run at a named lifecycle event, with an input and output contract for its source format     | [Hooks](../packages/coding-agent/docs/hooks.md), [what each format accepts](../packages/coding-agent/docs/hook-events.md) |

User code extensions no longer exist: the agent's own features register through an internal API (`src/core/features/`), and code named by a setting, a package or `--extension` is refused or ignored with a warning ([native features](../packages/coding-agent/docs/native-features.md#runtime-ownership)).

## Design

Each format is a separate profile over one runtime. `src/octocode/hooks/` owns discovery, profile selection, scheduling, payload adapters and result decoding; the existing runner owns process cancellation and output; core owns lifecycle events and validated tool execution; permission and collaboration own their own decisions. A file's source decides its profile: `.claude` files use the Claude profile, `.codex` files and Codex TOML the Codex profile, and Octocode files the native one. A handler is never deduplicated across profiles, because that could erase a policy.

The flow is: discover, trust, parse in the source's format, select by event, build that format's payload, run the transport, validate that format's output, combine decisions, apply them through the owning runtime, audit. A capability that is unsupported is reported and never treated as success.

An input rewrite is a transaction: translate it back to native input, validate it against the tool's schema, then check reservations and permissions again on the final arguments before the tool runs. No rewritten call runs under an approval given for the original.

Rejected alternatives: leaving the parser permissive (silently changed execution fields are correctness bugs), and adopting one host's hooks alone (both hosts are required).

## What is not implemented

Local adapters are not full host equivalence, and nothing here claims it.

- **Claude Mods.** A Mod needs an isolated module environment, its own `register(on, options)` owner, middleware around real operations with budgets and cancellation, permission-preserving adapters for each engine operation, and separate rendering in the terminal and web view. None of this exists. A plugin hook file containing `modules` is reported and not loaded.
- **Plugin components.** What is unfinished is listed under [remaining limits](../packages/coding-agent/docs/plugins.md#remaining-limits); for permission updates and rewrites, see [hooks](../packages/coding-agent/docs/hooks.md).
- **Vendor services.** Vendor accounts, cloud administration and managed policy have no local equivalent. Identical model-generated decisions from prompt hooks cannot be promised across models.

## How compatibility is checked

Normal tests read saved fixtures and need neither Rust nor a vendor binary. The commands below rebuild or replay them, against source revisions and executables pinned in each fixture's manifest. A fixture proves its own narrow contract, not host equivalence.

Does not cover exit semantics, timing, permissions or patch rewriting                                                                                                                                                                                                              | `node packages/coding-agent/scripts/generate-codex-hook-output-fixtures.mjs [--check]` (needs Cargo and network)                                           |
