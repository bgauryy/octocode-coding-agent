# Plugins, skills, extensions and hooks

Octocode has native extensions and skills, opt-in Claude/Codex hook adapters, and explicitly configured local plugins. The matrices below distinguish verified behavior from missing host contracts and define the implementation order. Full compatibility is not yet verified.

## Summary

The goal is full documented Claude Code and Codex compatibility across plugins, skills, extensions and hooks, with each component assessed separately. Implement two versioned protocol adapters over the existing process/runtime owners. Keep Octocode's current contract as a third profile for existing native configurations. Configuration acceptance, delivered input, applied output, event timing, discovery and failure behavior must all pass conformance checks before a matrix row becomes compatible.

Full host equivalence cannot currently be promised. Vendor cloud administration, account services and Claude-specific rendering surfaces have no established Octocode implementation; model-generated prompt/agent-hook judgments cannot be guaranteed identical across models. These are explicit gaps in the goal, not silently excluded successes. Implement portable contracts and identify the remaining host dependencies with evidence.

The baseline below is the current working tree on `a960a8290dc58980bb4215993a7e8ca16d4f399d`, including earlier hook fixes. Official contracts were read on 2026-10-22, with child identity and permission-request references rechecked on 2026-10-23. Retained Claude Code 2.1.309 permission, Bash grammar and wrapper probes establish narrow executable baselines; complete upstream conformance remains open. Docs can move independently of releases; pin fixtures and supported releases before calling a profile fully compatible.

### Plugins: packaging and component ownership

A plugin is not itself an executable extension or a skill. Parsing its manifest identifies its package and declarations; trust, component validation and activation are separate steps. Each component must enter its owning subsystem. Claude Mods are executable extension components and need their own compatibility adapter; their presence in a plugin does not make them native Octocode extensions.

Native Octocode packages currently distribute extensions, skills, prompt templates and themes using `package.json` or conventional directories. That existing support must not be presented as Claude/OpenAI plugin compatibility. Local enable/disable and shared writable plugin data are implemented. Marketplace services, plugin dependencies and install/update/uninstall management remain separate workstreams.

### Skills: instructions and supporting files

Skill discovery advertises the name, description and path; full instructions are loaded when requested or relevant. Skill commands and model selection of a skill are different from hook event dispatch. A skill may instruct the agent to run bundled scripts, but discovery itself does not execute those scripts. Supporting a `SKILL.md` format does not imply support for every host-specific skill field or skill-scoped hook declaration.

### Extensions: executable runtime integrations

Native extensions use the existing loader and API. They can listen to events without enabling command hooks. Discovery rules, including the plugin and skill marker rule, are stated once in [extension directory discovery](../packages/coding-agent/docs/extensions.md#extension-directory-discovery). Explicit native package declarations or directly supplied module files still enter the executable loader.

### Hooks: event contracts and execution

Hooks use `OCTOCODE_HOOKS=1`; the developing source-specific adapters additionally require `OCTOCODE_HOOKS_COMPAT=1`. The default mode reads supported entries from Claude/Codex files but applies Octocode behavior. The preview selects a profile by source and implements only the capabilities marked in the event/configuration matrix. Native extension event handlers are not this subsystem and do not require these flags.

The runtime discovers the seven files listed in the hook guide, merges supported entries, applies native project trust, and exposes diagnostics through `/hooks`. It additionally reads reviewed hooks from explicitly configured plugins. The source-profile preview also reads user and trusted project Codex `config.toml`, including inline hooks, Windows command aliases and the hooks feature switch. Arbitrary script discovery and managed Codex policy remain unsupported.

### Implementation boundary

Keep four independent responsibilities: plugin identity and declarations; skill loading and invocation; executable extension APIs and lifecycle; hook protocols and dispatch. A plugin may supply inputs to the other three, but cannot bypass their validation, trust, cancellation or cleanup rules. Track packaging compatibility separately from each component's execution compatibility.

### Original native baseline

This section describes the native profile before the compatibility work. The source-profile matrix and implementation sections below describe the added behavior.

- Command hooks run only with `OCTOCODE_HOOKS=1`. Discovery reads user Claude, Codex and Octocode hook files, plus trusted project files. Project Claude local settings are included. See [configuration locations](../packages/coding-agent/docs/configuration.md).
- Native-profile events are `PreToolUse`, `PostToolUse`, `SessionStart`, `PreCompact`, `Stop`, `Notification`, `PreMessageSend` and `PostMessageReceive`.
- File queries are translated to Claude-style Edit/Write/MultiEdit/Delete payloads. A batched file operation produces a dispatch per query. Some other names are aliases for matching only, not full input translations.
- A pre-tool denial blocks execution; `ask` reaches the permission gate. `allow` never bypasses Octocode permission checks. Post-tool hooks run for successful results and append feedback; they cannot undo effects.
- Session-start context reaches the next prompt. Stop hooks can request continuation within a bounded loop. Notification and received-message hooks are observers.
- The command runner retains process-tree termination, cancellation, bounded output, context spilling and optional `failClosed`. Project configuration trust is fingerprinted.
- Native extensions already register tools, commands, events, providers, MCP servers, virtual models and terminal UI. They execute with host permissions. See [Extensions](../packages/coding-agent/docs/extensions.md).
- Packages declare extensions, skills, prompts and themes through `package.json`'s `octocode` field, with a `pi` fallback. This is not an implementation of Claude or OpenAI plugin manifests.

### Corrections implemented in this change

| Previous behavior                                                                       | New behavior                                                                                                       |
| --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `matcher: "*"` was reported invalid but still matched                                   | The wildcard validates and matches consistently                                                                    |
| Unknown events and handler types vanished without explanation                           | Diagnostics name the source and skipped event or entry                                                             |
| A numeric matcher became an unrestricted matcher                                        | Invalid matcher types are rejected with a diagnostic                                                               |
| Unknown group/command fields were discarded while the command could execute             | The affected entry is rejected; valid siblings still load                                                          |
| Unsupported command fields on a required gate could be lost                             | A `failClosed: true` PreToolUse/PreMessageSend command remains a denying gate and starts no process                |
| Duplicate command text could hide that invalid required gate                            | Deduplication preserves the configuration failure and denial                                                       |
| `disableAllHooks` was ignored                                                           | Any loaded file with `disableAllHooks: true` disables all loaded hook sources                                      |
| Pre-tool `additionalContext` was parsed but discarded                                   | Unblocked, uncancelled hook context is sanitized, capped and sent as hidden context without starting an extra turn |
| Tool payloads lacked a correlation ID                                                   | PreToolUse and PostToolUse now include `tool_use_id`                                                               |
| Malformed `hooks` containers disappeared silently                                       | They now produce source-specific diagnostics                                                                       |
| `/hooks enable` and `/hooks off` silently displayed status                              | Unsupported arguments now explain startup enablement without pretending to toggle execution                        |
| `/hooks` claimed a generic Claude/Codex format and called all diagnostics invalid files | It now describes a command-hook subset and displays configuration diagnostics                                      |

## Goals and scope

The goal is to implement both pinned host contracts across the four separate systems, preserving permission ownership and native lifecycle protections. Existing user changes and compatibility fields are retained until their consumers have a migration path.

Full upstream parity, input rewriting, new event families, remote transports and unchanged Claude Mods execution are now in the implementation goal; they are not yet delivered. Validation uses local fixture plugins; no downloaded third-party plugin code was executed.

## Proposed design

Keep `src/octocode/hooks/` responsible for hook discovery, profile selection, scheduling, payload adapters and result decoding. Add cohesive profile modules there, rather than conditionals throughout `core/agent-session.ts`. Keep process cancellation/output handling in the existing runner. Core owns lifecycle events and validated tool execution; permission and collaboration owners retain their policy decisions. Plugin manifests normalize into the existing core resource pipeline. Mods use a deliberate native-extension bridge; they are not imported as arbitrary TypeScript extensions.

A loaded handler carries dialect, source identity, scope, event and execution context. Select Claude for Claude configuration, Codex for Codex configuration, and Octocode for native configuration once that profile's migration gate passes. Retain an explicit legacy route during migration; never silently switch a policy configuration whose new semantics are incomplete. Loading one of each must preserve both dialects in the same session. Identical commands in different dialects/plugins are not the same handler.

Process flow: discover → trust → parse in source dialect → select by event → construct dialect payload → execute transport → validate dialect output → combine decisions → apply through the owning runtime boundary → audit. Unsupported capabilities must be inspectable and must not become a false success. Preserve the native `failClosed` contract while defining upstream failure semantics separately.

Input rewrites are a transaction: collect/resolve according to the host contract, translate back to native input, validate the tool schema, then re-evaluate path reservations and permissions against the final arguments before execution. The present reservation-before-hook order cannot safely accept a path rewrite without this change. No rewritten tool may run under approval for its old arguments.

### Canonical patch execution in the file owner

The C11/C12 implementation adds `{patch: string, reason?: string}` as an alternative to native `{queries: [...]}` on the existing `file` tool. The two modes are mutually exclusive. Native queries keep their current failure behavior; canonical patches follow the pinned Codex preparation and execution order. A separate `apply_patch` tool or filesystem implementation inside hooks would duplicate ownership and is not selected.

The [pinned invocation verifier](https://github.com/openai/codex/blob/8eaf5fd115f036d207be236009938261758e30f2/codex-rs/apply-patch/src/invocation.rs#L180) prepares every operation and rejects duplicate resolved source paths before execution. A missing later Delete or invalid later Update therefore prevents an earlier Add. Runtime failure during mutation can still leave earlier effects; this is not a rollback transaction.

Implementation and verification order:

1. Add a pure parser and chunk transformer in the shared contract layer, with upstream attribution; keep filesystem effects in the file subsystem. Compare exact bytes and selected locations against pinned fixtures for Update, Move, EOF, whitespace matching and mixed line endings.
2. Extend the existing tool schema and shared mutation-target discovery. Permission review, reservations, provenance and activity reporting must include source and destination paths.
3. Prepare all changes through existing read/stale guards before the first mutation. Commit through existing mutation queues, locks and cancellation checks; retain checkpoints for both move paths. A source is removed only after its destination write succeeds.
4. Make accepted Codex hook rewrites select canonical mode, retaining the exact patch text for successful post observation. Keep native/Claude projections separate and fail explicitly when translation cannot preserve meaning.
5. Replay real-session tests for preparation failure, update/move bytes, partial reads, stale/racing files, destination denial, cancellation and rewind. Keep the native query regression suite unchanged.

The competing per-query `type: patch` approach fits existing rendering but obscures whole-patch preparation, multiple targets and stop-on-error semantics. Canonical mode makes those differences explicit. Retained Octocode read/permission safeguards and unsupported remote environment routing remain documented host differences. Native edits still need a reviewed-snapshot projection; syntax-only conversion cannot establish equivalence.

## Risks and mitigations

Stricter parsing can disable an automation that previously ran with ignored options. Diagnostics and regression tests make that change inspectable. Unsupported fields on valid required gate commands deny matching calls; malformed configuration still requires operator review.

The conservative disable switch is intentionally broader than source-host precedence. Its source-specific diagnostic and documentation are part of the contract. It must never read untrusted project files.

Hook context increases model-visible content. Existing sanitization and byte limits remain; block/cancellation checks prevent delivering context from those outcomes. Native extensions and shell hooks still run with host privileges; this work does not create a sandbox.
