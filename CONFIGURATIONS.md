# Configurations

Use `~/.octocode/octocodecode/` for global core configuration and `.octocode/` for workspace configuration. MCP definitions are the exception: the canonical global file is `~/.octocode/mcp.json`, and the canonical workspace file is `.octocode/mcp.json`. Start Octocode in the workspace you want to configure. Run `/mcp config` to see the exact MCP paths, their read order, and whether workspace files are trusted.

`OCTOCODE_HOME` changes the shared configuration and runtime home. `OCTOCODE_CODING_AGENT_DIR` changes only the core configuration directory; native runtime files keep their own home. Explicit home overrides disable automatic Pi configuration fallback. See [configuration and compatibility](packages/coding-agent/docs/configuration.md).

`OCTOCODE_AGENT_DB` selects the native SQLite file. Shared connections are keyed by canonical path and remain open until process cleanup; selecting another file does not close existing borrowers. Interface runtime state stays in memory. History rows (audits and web command receipts) older than 14 days move to gzip monthly files in `<octocode home>/archive/`, even when `OCTOCODE_AGENT_DB` points elsewhere, and are dropped after 30 days; backlog items are never deleted by age. See [runtime storage](packages/coding-agent/docs/configuration.md#runtime-storage) for the database and file boundaries.

Workspace memories, agent lifecycle events and complete compaction summaries also use this database and are not deleted by age. `.octocode/agents.txt` is a generated view of its latest 50 workspace events, bound to the first configured database; removing that generated file permits rebinding. Archive detail copies use `OCTOCODE_CLEANUP_DAYS` (default 30, zero disables), measured from committed compaction time; original transcripts remain. No workspace marker or separate note store is created. See [Memory and Archive](packages/coding-agent/docs/memory.md).

Trusted workspace settings override global settings. Objects merge recursively; arrays replace rather than append. Resource settings such as `skills`, `prompts`, and `themes` support additional paths and selection patterns through their loaders; `extensions` accepts only `builtin:<id>` entries. The [settings reference](packages/coding-agent/docs/settings.md) lists every field with its default, including trust, telemetry, proxy and shell settings; the [settings schema](packages/coding-agent/schemas/settings.schema.json) validates them. A root key the schema does not define still loads and is preserved on save, but has no effect; Octocode warns about it once per load, naming the key and, for removed keys such as `compaction`, what replaced it. Non-interactive modes are described in [CLI modes](packages/coding-agent/docs/cli.md) and [RPC mode](packages/coding-agent/docs/rpc.md).

**Session titles.** Automatic titles are on by default; set `sessions.autoTitle` to `false` in `settings.json` to turn them off, and name a session yourself with `/rename <name>` or `--name`. After the first turn of an unnamed session in the interactive terminal or RPC mode (never `-p`/print or JSON), Octocode asks the cheapest capable model it can resolve (the model the `small` purpose resolves to, shown by `/modelsettings`) for a title of at most 6 words that keeps your own key words, sending that model the session's first message, and records it as a `session_info` entry with source `auto`; a name you give with `/rename` always replaces it and is never overwritten. With no cheaper model resolvable (the session model's price is unknown, or none is connected) nothing is called and the first prompt stays the title. When the model answers that the message names no task (a greeting, `ping`), the next turn tries your next message, up to the third; after that, or after a failed or timed-out call (20 s), the first prompt stays the title until the session is compacted: then one more call (once per run) is made with the summary's Goal section, never replacing an auto title or your name. A subagent's session is named for its goal. The `sessions` table of the agent database caches each session's title, folder, file, first prompt, message count and times so `/resume` can list without parsing transcripts; the transcript stays the source of truth, and a file modified after its row was written is parsed again. `agents.session_id` records the session a main agent runs, so a `/resume` row can show the agent name only while that agent row exists; a backlog item's `assignee` (kept on `done`) is how `/resume B<n>` finds its sessions.

**Worktree files.** `.worktreeinclude` at the root of the checkout you start from (gitignore syntax) lists untracked files, such as `.env`, that `octocode --worktree <name>` and `/worktree new` copy into a newly created worktree; existing files are never overwritten, symlinks are skipped, dependency and build folders such as `node_modules` are left out unless a line names them, and at most 2,000 files and 100 MB are copied. Those worktrees live in `.octocode/worktrees/<name>` under the main checkout; add `.octocode/worktrees/` to `.gitignore`. They inherit the main checkout's project trust while their trust-gated files are byte-identical to the trusted ones; Octocode records them in `worktree-origins.json` in its home folder (`OCTOCODE_HOME`). See [worktrees](packages/coding-agent/docs/native-features.md#worktrees).

Run `octocode config` to select built-in extensions as well as installed resources. Built-in names and enable/disable settings are described in [built-in features](packages/coding-agent/docs/configuration.md#built-in-features).

`/web` opens the local web workspace for the current session. Its private server registry is stored in `workspace-web/` beside the configured agent database and keyed by repository and session.

**User-level web daemon (opt-in).** With `OCTOCODE_WEB_DAEMON=1`, `/web` starts or reuses one detached daemon per OS user instead of a per-session server, and falls back to the per-session server if the daemon cannot start. Unset or `0` keeps the per-session behavior and starts nothing. The daemon outlives the session that launched it, serves one origin (`http://127.0.0.1:<port>`) with a session list, a read-only board and reports for every repository in the agent database, and a Settings page that shows provider credential sources and edits `defaultProvider` and `defaultModel` in the global file, or in the workspace file of a trusted repository, and sets, replaces or clears a provider API key (launch link only; a `/remote` link is read-only; running sessions pick changes up with `/reload`). A key goes to the OS keychain first and `auth.json` receives only the keychain reference; the keychain write is undone, while the `auth.json` lock is still held, if `auth.json` cannot be written, and a keychain that refuses is never replaced by plaintext. A failure message says "Nothing was changed" only when that is true; when the keychain could not be restored, or `auth.json` could not be read back, it says the key may have changed. Clear removes the `auth.json` entry and then the keychain entry; if the keychain entry cannot be removed the `auth.json` reference is put back and Clear reports an error, so a retry works. On a host with no OS keychain (for example Windows) a key is saved as plain text in `auth.json` only after the page's explicit confirmation, and an existing `auth.json` that group or others can read is changed to owner-only (0600) first; if that fails the key is not saved. A provider signed in with OAuth must be cleared before a key is set (checked again under the `auth.json` lock). Provider ids the credential endpoint would refuse (anything outside `[a-z0-9][a-z0-9._-]*`) are listed read-only. The key is never returned: the page shows only whether a credential exists and its source kind. Each attempt adds a `config_audits` row in the agent database (actor, provider, source kinds before and after, outcome, error code; never a key); a malformed request from the launch page adds a `credential.refused` row with a fixed code and no provider. Requests without a valid token are not recorded, so a caller that can reach the port cannot grow the log. The daemon exits after `OCTOCODE_WEB_DAEMON_IDLE_MINUTES` (default `10`; decimals allowed) with no open tab, no attached session and no device connected through a `/remote` relay. Its state lives in `<octocode home>/web/` (`OCTOCODE_HOME`, default `~/.octocode/octocodecode`), a 0700 directory:

| File                                            | Written by                                           | Purpose                                                                                                                                         |
| ----------------------------------------------- | ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `web/daemon.json` (0600)                        | the daemon, after it listens                         | pid, process start time, port, URL with the launch token in the fragment, protocol version, build and per-start nonce; removed on exit or drain |
| `web/daemon.launch.lock`, `web/daemon.run.lock` | launchers (briefly), the daemon (for its whole run)  | one daemon at a time; a lock left by a dead process is broken at once                                                                           |
| `web/attach/<sessionId>.json` (0600)            | each non-subagent session at start, with the flag on | loopback attach port and the session's own 32-byte token; removed at session shutdown                                                           |

**Remote access.** `/remote` publishes the daemon for another device: a control link (the page's full surface) or a view-only link, over `remote.transport` `ssh` (the daemon's own page behind a port forward the user runs; nothing new listens) or `relay` (the daemon dials `remote.relayUrl` and publishes end-to-end sealed frames; the key stays in the link's fragment). `remote.autoStart` (`off`, `view`, `control`) publishes a link when a session starts; a project settings file may set it to `off` but can never turn it on. A published control link carries a separate remote token that cannot use the daemon's admin routes, and `/remote stop` replaces it and the view token, so every link dies. `octocode remote list --json` reads the sessions and the links (by fingerprint, never the capability) from the running daemon. See [remote access](packages/coding-agent/docs/remote.md).

Sessions keep execution and permissions: the daemon forwards commands over the attach connection and never runs agent work. The board is read-only in the daemon; edit it from a session's own `/backlog`. A daemon of another build (package version plus page hash) is asked to drain when a launcher of a newer build runs. The daemon accepts only the `Host` `127.0.0.1:<port>`, sends no CORS headers, needs the bearer token for every route except `GET /` and `GET /api/health`, and serves the page with a script-hash Content-Security-Policy. See [interface architecture](docs/INTERFACE_ARCHITECTURE.md#user-level-web-daemon). Different sessions share repository entities in the database while keeping their live controls separate. See [the backlog view](packages/coding-agent/docs/web-workspace.md#backlog-view) for concurrent editing and reconnect behavior.

Inline terminal images use `terminal.showImages`, `terminal.images`, and `terminal.imageWidthCells`; automatic capability detection and explicit overrides are described in [terminal images](packages/coding-agent/docs/configuration.md#terminal-images).

Set `terminal.reduceMotion` to `true`, `false` or `"auto"` to freeze terminal animation; `"auto"` follows the `OCTOCODE_REDUCE_MOTION` environment variable (see [reduced motion](packages/coding-agent/docs/configuration.md#reduced-motion)).

Settings, MCP configuration, and project trust saves replace the target file atomically, so a concurrent reader sees a complete old or new document. Settings saves also lock the read–merge–write operation, including first creation, so cooperating writers preserve each other's unrelated changes. An empty settings file or one whose root is not a JSON object is reported as invalid and is not overwritten by a settings change, including when the file becomes invalid after startup; repair the file, then run `/reload`.

**Folder trust gate.** Octocode opens no session in a folder the user has not trusted. Trust records live in the agent database (`trusted_folders`); a grant covers a folder or, for a parent or grandparent, its subtree, and trusting a folder trusts its future contents (no content fingerprints). Before the decision nothing is read from the folder (no `AGENTS.md`, `CLAUDE.md`, settings, MCP, hooks, skills, agents, plugins or `SYSTEM.md`), no model is called and no tool exists; the prompt lists project file names only. Interactive runs show the prompt; "Do not trust" is recorded and the next open exits with a hint (`/trust` or `octocode trust add <path>`), while "Not now" records nothing. Print, JSON and RPC runs in an undecided folder exit non-zero; ACP answers `session/new` with a per-session `-32002` error and the server stays up. `--trust` records your grant (source `flag`) and then runs. `--trust` does not apply to `--mode acp`. `$HOME`, `/` and other filesystem roots never get a session or a grant, and no folder above `$HOME` (`/Users`, `/home`) gets a subtree grant (the prompt does not offer it and an existing row is ignored with a notice). `--trust` over a remembered "Do not trust" records the grant and prints that it replaced the refusal. `octocode trust add|remove` and `--trust` refuse to record when `OCTOCODE_SESSION_ID` is set, that is, when run from the shell of a session: trust is the user's decision, so run them in your own terminal. A running session that moves into another folder (`/resume`, `/import`, a new session or `/worktree switch` with a `cwd`, RPC `switch_session`) checks trust before the current session is touched: the TUI shows the trust prompt in the session and keeps the old session with a warning when you decline; RPC and print return an error and keep the session. Once trusted, `AGENTS.md` and `CLAUDE.md` load from the folder the grant is on down to the working folder, not from every parent up to `/`. A new worktree (`/worktree`, `--worktree`, isolated subagents) asks once before `git worktree add` (when its source repository is not trusted either, the question says so and defaults to No); yes records a `worktree` grant, no creates nothing, headless runs need `--trust`, and removing the worktree revokes the grant. Subagents never prompt or record: they run only in a trusted folder, and `OCTOCODE_TRUST_ROOT` is no longer set. A `trust.json` or `pi-trust.json` from an earlier release is not read: trust the folder again with `octocode trust add <path>`.

Project resources require project trust, except project instruction files such as `AGENTS.md`, which load as text (see [instruction loading](packages/coding-agent/docs/instructions.md#user-instructions-and-subagent-roles)). Folder trust is managed with `/trust` (a menu; `/trust list`, `/trust add [path] [--scope folder|parent|grandparent]`, `/trust remove <number|path>`) and, without a session, `octocode trust list [--json]`, `octocode trust add [path] [--scope ...] [--yes]` and `octocode trust remove <number|path> [--yes]`; `--yes` skips the confirmation for scripts, and the list shows each grant, refusal and ignored home or root grant with path, scope, source and date. The trust prompt offers the folder, its parent and its grandparent (each a subtree), "Not now" and "Do not trust"; parents that are your home folder or a filesystem root are not offered, and `$HOME` or `/` opens no session (open a project folder instead). Opening a worktree Octocode creates asks once: "Trust new worktree <path> (from <repo>)?". Hooks are always on: Octocode reads Claude and Codex hook files (including Codex TOML) under their own partial profiles and Octocode hook files under the native contract; `disableAllHooks: true` in any loaded hook file turns them off. The [Claude permission rules](packages/coding-agent/docs/permissions.md#claude-permission-rules) from the same settings always apply, independently of hook execution. `/harness hooks` inspects configuration rather than toggling it. See [command hooks](packages/coding-agent/docs/hooks.md) for discovery, trust, disable behavior and supported events. See [native features](packages/coding-agent/docs/native-features.md) and [instructions](packages/coding-agent/docs/instructions.md) for their behavior.

## Manage MCP servers

| Task                                          | In an Octocode session                               | From a shell                                                              |
| --------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------- |
| Open the manager                              | `/mcp`                                               | —                                                                         |
| Show connection state                         | `/mcp list`                                          | `octocode mcp list`                                                       |
| Show configuration locations                  | `/mcp config`                                        | `octocode mcp config`                                                     |
| List tools                                    | `/mcp tools` or `/mcp tools <server>`                | `octocode mcp tools [server]`                                             |
| Inspect a tool's description and input schema | `/mcp tools <server> <tool>`                         | `octocode mcp tools <server> <tool>`                                      |
| Enable / disable a server                     | `/mcp enable <server>` / `/mcp disable <server>`     | `octocode mcp enable <server>` / `octocode mcp disable <server>`          |
| Change tool exposure                          | `/mcp exposure <server> hidden`                      | `octocode mcp exposure <server> hidden`                                   |
| Assign a server to the agents that name it    | `/mcp assign <server> selected` (`all` to undo)      | Set `"defaultActive": false` in `mcp.json`                                |
| Reconnect                                     | `/mcp reconnect <server>`                            | `octocode mcp list` checks a fresh connection                             |
| Sign in / out                                 | `/mcp login <server>` / `/mcp logout <server>`       | `octocode mcp login <server>` / `octocode mcp logout <server>`            |
| Add / remove a definition                     | Edit the file shown by `/mcp config`, then `/reload` | `octocode mcp add [--local] …` / `octocode mcp remove <server> [--local]` |

Add `--local` (shell short form `-l`) to enable, disable, add, remove or change exposure in a **trusted workspace**; for example `octocode mcp add --local docs --url https://example.com/mcp`. Without it, an existing workspace definition or override remains the save target; otherwise global changes save to the canonical global file. The manager shows the exact target before you choose an action. Shell `add` and `remove` target the global native file by default, or the workspace native file with `--local`.

Enablement defaults to **true**. Disabling keeps the definition, stops its connection, and removes its callable tools. Exposure defaults to **direct**: every tool of a selected server is declared up front, described, with the server's instructions, in one block per server of the cached system prompt: a generated TypeScript file (`mcpPresentation: "compact"`, the default; stored under `<agent directory>/context-optimization/mcp/`, safe to delete) or, with `"json"` in `settings.json`, the description and JSON Schema as the server sent them. Provider declarations stay thin either way. `hidden` prevents calls while leaving the server connected, and a `toolExposure` map can override individual tools. `defaultActive: false` keeps a server out of every agent's default tool selection, so only agents whose selection names `mcp__<server>__*` start and use it. See [exposure rules](packages/coding-agent/docs/mcp-reference.md#exposure-and-results) and [assignment](packages/coding-agent/docs/mcp-reference.md#assign-servers-to-agents).

Stdio servers receive only a minimal environment by default (the MCP SDK allow-list: `HOME`, `LOGNAME`, `PATH`, `SHELL`, `TERM`, `USER`; a Windows set on Windows) plus the configured `env`; `inheritEnv: true` passes the whole host environment, tokens included; command and arguments work with binaries, Python, Node, and container launchers.

`/mcp tools` inspects the current connection snapshot without invoking tools or enabling disconnected servers. In the manager, select **Tools**, then a tool to inspect its complete description and input schema. The shell tool-list command connects enabled configured servers; selecting one server avoids connecting the others. `list`, `tools`, and `config` support `--json` in the shell.

Octocode research is the default entry in the shared MCP host registry, implemented by the private [MCP workspace](packages/mcp/README.md). The `octocode` preset supplies launch and tool-presentation defaults; configured and registered servers use the same connection and management paths. `/mcp enable octocode`, `/mcp disable octocode` and `/mcp exposure octocode <mode>` save control-only overrides, so an explicit command is unnecessary. `OCTOCODE_MCP=0` disables the default unless configuration overrides it. The whole Octocode catalog is declared like any other server's. Shell MCP commands load the same default and configuration. `mcp({ intent: "stop", server: "octocode" })` stops it for this session; only an explicit connect/restart resumes it. The `browser` preset is a second default entry, powered by `@octocodeai/octocode-chrome-devtools`, with `defaultActive: false`: only the `browser` subagent selects and starts it, and the main agent delegates to it. `/mcp disable browser` saves the same kind of control-only override, and `{ "mcpServers": { "browser": { "defaultActive": true } } }` gives it to the main agent; a subagent starts it only when its profile names `mcp__browser__*`. A `defaultTools` entry per tool (for example `+mcp__browser__open`, `+mcp__browser__run`, `+mcp__browser__snapshot`, `+mcp__browser__screenshot`, `+mcp__browser__check`, `+mcp__browser__cleanup`) gives the main session a trimmed browser instead. Browser calls that leave the isolated browser (real profile, another Chrome binary, cookie or download CDP, uploads from outside the workspace) ask `browser.control` or `upload.outside` and are refused in read-only roles. See the [MCP reference](packages/coding-agent/docs/mcp.md#host-and-protocol-support) and the [browser preset](packages/coding-agent/docs/mcp-reference.md#configuration-and-precedence).

The research server's local readers reach the workspace, the session folders and loaded skill folders. To add folders, list them in the global `settings.json` `research.allowedPaths` (see [settings](packages/coding-agent/docs/settings.md)), in `ALLOWED_PATHS` of `~/.octocode/.env`, in `local.allowedPaths` of `~/.octocode/.octocoderc`, or in the `ALLOWED_PATHS` environment variable. All four add to the defaults; project files cannot add folders, and the filesystem root, your home folder, the Octocode home and credential folders are refused with a warning. Only an `ALLOWED_PATHS` in the `octocode` entry's own `env` in `mcp.json` replaces the whole list.

After changing files or using shell configuration commands, run `/reload` in existing sessions. Session `/mcp` enable/disable/exposure actions apply immediately. The host supports tools only; elicitation, resources and annotations are unsupported. Cached catalogs contain full tool descriptions, schemas and server instructions in memory; disabling or disconnecting withdraws them, and reconnecting refreshes them. With `mcpPresentation: "compact"` each server's generated TypeScript is stored with its metadata in one atomic JSON snapshot under `context-optimization/mcp/` in the agent directory (moved there from `mcp-generated/` on first use); the `.txt` file is an inspection copy. See [compact presentation](packages/coding-agent/docs/mcp-reference.md#compact-presentation) for regeneration and refresh behavior.

### MCP precedence

With the default home, global files are read from lowest to highest priority:

1. `~/.pi/mcp.json`
2. `~/.pi/agent/mcp.json`
3. `~/.octocode/agent/mcp.json`
4. `~/.octocode/octocodecode/mcp.json` (previous native location, still read)
5. `~/.octocode/mcp.json` (canonical global file)

Trusted workspace files then apply in this order: `.pi/mcp.json`, `.mcp.json`, `.agents/mcp.json`, `.octocode/mcp.json`. Each path is relative to the session directory. A later transport definition replaces the earlier server with the same name; a later control-only entry changes `enabled`, `exposure`, `toolExposure` or `defaultActive` without copying credentials. `/mcp config` shows the actual paths when your home is overridden. Workspace MCP files load only in a trusted folder; trusting the folder covers files added or edited later, so run `/reload` after a change.

For example, after defining `docs` globally, this workspace `.octocode/mcp.json` disables it only for that workspace:

```json
{
	"mcpServers": {
		"docs": { "enabled": false }
	}
}
```

Removing an override can reveal an inherited server again. Use disable when you want an inherited server to remain off. [MCP configuration](packages/coding-agent/docs/mcp.md#configure-servers) owns the complete transport, authentication and override rules.

## ACP clients

An editor can launch `octocode --mode acp` to control Octocode through inbound ACP v1. It uses the normal host credentials, settings, project trust and `OCTOCODE_PERMISSION` policy; no separate ACP configuration file is required. The client supplies each session's working directory. Stdio and Streamable HTTP MCP definitions supplied with `session/new`, `session/load` or `session/resume` are registered temporarily for that worker through the shared MCP host. Environment and header values are literal; definitions are not written to global or workspace `mcp.json`. In-protocol model or permission-mode changes are not supported. See the [ACP reference](packages/coding-agent/docs/acp.md) for invocation, permissions and session limits.

The native `agent` tool's `type: "external"` / `transport: "acp"` connection is outbound ACP to another agent. `/api` and `octocode-api` expose the separate [local session API](packages/coding-agent/docs/session-api.md).

## Skills and prompts

Put a skill's instructions in `<name>/SKILL.md`, with `name` and `description` frontmatter. The Octocode skills bundled with the build load by default and, on a same-name collision, beat user-level copies the Octocode CLI installed (`~/.agents/skills/`, `~/.claude/skills/`, `$CODEX_HOME/skills/`, `~/.pi/agent/skills/`); `--skill` paths, `skills` settings entries, packages, project `.octocode/skills/` and `.agents/skills/`, and the agent directory's `skills/` beat the bundle. Shared `~/.agents/skills/` and project `.agents/skills/` directories are supported, and from a subdirectory the repository root's `.octocode/skills/` is a project folder too; project ancestor discovery stops at the repository root. Native sessions also load `~/.claude/skills/` (without `synced/`), `$CODEX_HOME/skills/` and, in a trusted project, `.claude/skills/` up to the repository root; these load after the folders above, and `skills` patterns apply to them too. `/status` lists loaded skill paths and MCP connection status, while `/skills` offers a searchable picker.

Use `skills` patterns in settings to exclude or include discoveries, for example `"skills": ["!octocode-roast"]`. `--no-skills` disables automatic discovery. Setting `enableSkillCommands` to `false` hides autocomplete suggestions; it does **not** disable skills. See [skills](packages/coding-agent/docs/skills.md) for invocation, priority, bundled skills and access through Octocode local tools.

Prompt templates are Markdown files in `prompts/`. Skills and prompts get direct slash names when unambiguous, with `/skill:<name>` and `/prompt:<name>` fallbacks for collisions. See [prompt templates](packages/coding-agent/docs/prompt-templates.md) and [packages](packages/coding-agent/docs/packages.md) for additional resource locations.

## Models and credentials

Use `/login` for provider access, `/model` to select a model, `/effort` to choose reasoning effort, `/context size` for a session context budget, and `/modelsettings` for model shortcuts, catalog and routing. Put custom endpoints and model definitions in the global `models.json`; the [models guide](packages/coding-agent/docs/models.md) has examples and the [models configuration reference](packages/coding-agent/docs/models-configuration.md) describes each field.

Use `octocode models discover [--provider <id>] [--json]` to compare vendor lists with configured model IDs; `--offline` and `OCTOCODE_OFFLINE=1` use only local definitions. See [vendor model discovery](packages/coding-agent/docs/model-discovery.md). ChatGPT logout retains nonsecret account/client registrations in `auth.json` for returning login while removing tokens; these signed-out records do not mark the provider as configured.

Default selection uses `defaultProvider` and `defaultModel` in settings. Authentication lives in global `auth.json` or environment variables; MCP OAuth uses the separate global `mcp-auth.json`. Gemini recognizes both `GOOGLE_API_KEY` and `GEMINI_API_KEY`, with `GOOGLE_API_KEY` taking precedence; Meta recognizes `META_API_KEY` and the Model API's `MODEL_API_KEY`, with `META_API_KEY` taking precedence. Explicit Bedrock credential-chain and Vertex ADC login delegate credential resolution to their SDKs. Keep credentials out of shared workspace files. Provider/model settings can select cache retention; paid cache warming is controlled by global settings. See [providers](packages/coding-agent/docs/providers.md), [environment variables](packages/coding-agent/docs/environment-variables.md), and [prompt caching](packages/coding-agent/docs/prompt-caching.md).

Pi settings and provider definitions are fallback inputs when using the default home; native values take precedence and writes go to Octocode files and never contain a Pi value. Settings read, lowest first: Pi `settings.json` (global, then in a trusted folder `.pi/settings.json`), the Octocode global file, then the trusted `.octocode/settings.json`. Pi authentication is imported only through explicit confirmation in `/login pi`; trust decisions are not imported. Details remain in [configuration and compatibility](packages/coding-agent/docs/configuration.md).

Pi files, read only with the default home (an explicit `OCTOCODE_HOME` or `OCTOCODE_CODING_AGENT_DIR` turns them off): global skills, prompts and themes from `~/.pi/agent/` and `~/.pi/`; a global `AGENTS.md`, `SYSTEM.md`, `APPEND_SYSTEM.md` and `keybindings.json` from `~/.pi/agent/` (Octocode's own file wins); and, in a trusted folder, project `.pi/skills`, `.pi/prompts`, `.pi/themes`, `.pi/SYSTEM.md` and `.pi/APPEND_SYSTEM.md` under the same folder trust as `.octocode/`. Named collections rank scope first, then product (so a Pi project skill beats an Octocode global one, and Octocode beats Pi at one scope); single-valued files rank product first; `models.json` and `settings.json` are layered (every file is read, Octocode over Pi). Models, settings, agents, hooks, plugins and MCP servers are listed by the same discovery service (`octocode/discovery/` registers the kinds Octocode owns). Pi TypeScript extensions and hooks are never loaded: they are listed at startup as "Pi extension, not loaded". See [Pi configuration fallback](packages/coding-agent/docs/configuration.md#pi-configuration-fallback).

The startup screen and `/harness config` show what loaded and where each item came from (one `ConfigDiscovery` walk plus what the session's loaders loaded, in `core/discovery/context-view.ts`). Each kind is a row with a count and its sources (`octocode global`, `octocode project`, `pi global`, `pi project`, `plugin <name>`, `builtin`, `command line` for a flag and `settings path` for a path a setting names); a shadowed copy names its winner, a project item in a folder that is not trusted reads "folder not trusted", and Pi or other user code that Octocode does not run is one "Not loaded" row (`legacy.ts (pi global) · convert to hooks.json or a plugin`), stated once: the Warnings row holds only shadowed copies and untrusted items. `ctrl+o` lists every item with its path (a `(ctrl+o to expand)` hint shows while anything is collapsed). `/harness config` puts each path on its own line, cut from the left to fit a narrow terminal. `/harness config` prints the same view as text (read-only, also in RPC and print modes). The view refreshes on `/reload` or a new session, with no file watcher. The first start that finds Pi items prints a one-line notice once, recorded in `pi-notice.json` in the agent directory (delete the file to see it again).

Image-capable models use `"input": ["text", "image"]` in native or Pi-compatible provider model definitions and `modelOverrides`. Custom definitions without `input` default to text-only. Image request limits use the existing `inputLimits` fields; see [model input and caching](packages/coding-agent/docs/models.md#describe-model-input-and-caching) for examples and send-time validation.

Native workflow controls: `OCTOCODE_EDIT_DIAGNOSTICS=0` disables advisory edit diagnostics; `OCTOCODE_SUBAGENT_LINGER_SECONDS` retains eligible finished background workers for message follow-up within its bounded window; `OCTOCODE_SUBAGENT_STARTUP_RETRY_SECONDS` (0-600) bounds how long a subagent that crashes while loading its code is started again; `OCTOCODE_SUBAGENT_MAX_REQUESTS` limits cumulative saved assistant replies across the same child's continuations (profile `maxRequests` takes precedence; `0` disables it); `OCTOCODE_SUBAGENT_THINKING` sets the thinking level of a child whose call and profile name none (default `medium`; a child never takes `defaultThinkingLevel`, which is the main session's, built-in default `high`); the `bashBackgroundAfterSeconds` setting (default 90, `0` off) or `OCTOCODE_BASH_BACKGROUND_AFTER_SECONDS` sets when a foreground `bash` command moves to the background. The `bashOutputMaxBytes` setting (default 24576, at least 1024) caps the bytes of one foreground `bash` result that reach the model (the line limit scales with it); the call parameter `maxOutputTokens` lowers it for one call. The same cap applies to the output of the user's `!` commands that reaches the model. `debug` is opt-in: `--tools +debug` or a `defaultTools` entry declares it; the `agent` tool declares its `external` type only when a known ACP agent is on `PATH` or another Octocode instance runs, and a subagent declares `backlog` only when its task names a backlog item; browsing uses the built-in `browser` MCP server (the native `browser` tool was removed; a `defaultTools` entry for it is reported as having no effect); `bash` accepts `verify: true` per invocation. See [native features](packages/coding-agent/docs/native-features.md) and the [environment reference](packages/coding-agent/docs/environment-variables.md).

Subagent prompt-cache grouping is runtime state, separate from configuration files and transport session identity. See [prompt caching](packages/coding-agent/docs/prompt-caching.md#subagent-prefixes) for cache-key propagation, per-message accounting and compaction notifications.
